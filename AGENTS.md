# 2D Game Studio — notes for future development sessions

Read `README.md` (what exists) and `TODO.md` (what does not yet) and inspect the current repository before proposing changes. This is a visual game-making tool used by children, and hundreds of existing games have been saved. The TODO is a collection of ideas and reports, **not** a list of verified bugs or approved feature designs.

## Working agreement

- **Advice and patches only.** Never push to GitHub, create remote branches or pull requests, commit changes, or modify this repository on the user's behalf. Provide **one combined patch** based on the current branch for the user to inspect and apply locally (`git apply` or `git am`), even when the work has several parts, and give every patch file a name that starts with `2d-` (e.g. `2d-level-flow-and-hud.patch`). Do not assume a previous patch or this file has been applied. The user renders the recipes after applying a patch; check them (`npm run check`, which records and verifies but writes nothing) only when a change could break one, and say so if that was skipped.
- **Saved JSON is a compatibility contract.** Old game descriptions must load unchanged. Preserve existing trait/state/property names, array layouts, defaults, references, and the meaning of absent fields. Do not require users to migrate or re-export games. New features should use optional fields with legacy-compatible defaults. When modernizing mechanics, prefer a runtime compatibility adapter over rewriting stored JSON; keep legacy semantics and define explicit precedence if old and new fields coexist. Compatibility is one-way: saving may write a newer format, because only the current code reads saved games. `fix_game_data` must stay deterministic (the same JSON always normalizes to the same result), since content-derived tags and recipe fingerprints depend on it.
- **Preserve established gameplay.** Runtime internals may change, but assess any visible change to old games. Identify an intentional bug fix and its compatibility implications instead of silently changing existing behavior. Do not enable formerly ignored level-completion conditions for old games without a compatibility strategy. Their editor is gone (it had no markup any more); `level.conditions` stays in the data exactly as `fix_game_data` writes it (`touching_level_complete` by default, the `need_sprite` reference walker in `game_ids.js`), so saved games and recipes do not change.
- **Small, focused patches.** Implement one agreed issue or milestone at a time, explain the change and give practical checks for existing and new games. Add focused automated tests where they help; never substitute isolated tests for browser/gameplay verification.
- Keep the visual trait-based editor approachable. Separate **control**, **movement/physics**, **abilities** and **presentation** where practical; combine capabilities through traits instead of hardcoding platformer-only character classes. Do not begin a wholesale ECS/physics rewrite.

## Established behavior and design boundaries

- **Seamless interiors are built with Signale:** a Signalbereich over the house sends its Code while the player's centre is inside, and the facade/roof layer reacts with "weg, solange an" (optionally fading). There is no separate visibility system any more: old Sichtbarkeitsbereiche (`visibility_region` layers) are promoted to Signalbereiche on load (see Signale). Facade/roof art should have collision disabled, because a layer that is away also does not collide.
- **Combat foundation is implemented:** Shared actor/baddie melee, ranged projectiles and timed bombs; preserve legacy attacks and J/K/F controls. New attack families must use the same owner-neutral combat machinery for actor and baddie from their first playable version rather than creating a second enemy-only or player-only damage system.
- **Unverwundbare Gegner:** `traits.baddie.invincible` (drawing-level, default false): `Character.take_damage` ignores all damage for it (combat, falling blocks, anything added later) and `CombatSystem.apply_hit` refuses the hit before any damage or hit effect; a projectile still stops at it. Its own attacks and contact damage are unchanged. New damage sources must go through `take_damage` or `apply_hit` so this keeps holding.
- **Combat rules are independent of artwork:** Delivery, targeting, damage, timing and hit geometry come from combat configuration and runtime state, never from image pixels, frame count or sprite colour. Optional attack/hit/death animation states are presentation and must not silently change damage or collision semantics. Projectiles and other attack visuals likewise do not inherit unrelated placed-sprite traits.
- **Future combat stays incremental:** Instant lasers/rays, reusable area attacks, cooldown feedback and finite ammunition remain separate backlog items. A continuous beam is a distinct mechanic from an instant ray because it needs explicit re-hit/interrupt timing.
- **Collaboration is explicit and capability-by-link:** Do not introduce accounts, ownership or private-game permissions just to support live collaboration. A normal public game code may continue to let anybody open and save a descendant, but joining an active shared editing session requires its own hard-to-guess temporary session link/code. Every participant supplies a session-local display name; use it for presence and lock/conflict messages, but never treat it as authentication or durable ownership metadata. Address sprites and levels by their durable `id`, never by array index; keep session-only metadata (participants, locks, revisions) out of saved JSON. Prefer server-authoritative revisions and small resource leases/locks for the first implementation over a wholesale CRDT rewrite. The server never interprets references between resources; every editor action that adds, deletes or moves a sprite or level must call `window.collaboration?.structure_changed(kind, action, id)` after changing the local list (and lists offer `can_delete_index` so a locked item cannot be deleted). Anything that replaces the studio's game with another one must not do so silently during a session: `game.load()` is already guarded, other paths call `window.collaboration.confirm_leave('load', proceed)` first. Switching between sprites or levels must not flash or dim the editor: a resource is editable at once unless somebody else holds its lock; the client keeps the last server-confirmed value of every resource (`server_values`), sends what differs once its lock arrives, and undoes it if somebody else was faster. Showing a sprite must not change its data (the canvas does not re-encode a frame it only displays). Participant colours are indices handed out by the server (`COLOR_COUNT` in `collaboration.rb`) and mapped to `COLLABORATION_COLORS` in `collaboration.js`; keep both lengths equal. Shared saves must still go through the established immutable game/version path. `raw/collaboration/sessions.json` holds session codes and reconnect tokens: never move it below `gen/` or anywhere else nginx serves.
- **Als eigenes Spiel weiterführen starts a new game, never edits the old one** (`src/static/own_game.js`, Einstellungen → Spiel): after asking for a new title and the author, the current state is saved with `parent: null` and a fresh random top-level `lineage`, so it becomes a root (a new entry in the game list) with its own code even if nothing changed; later saves descend from it. `lineage` exists only to make the content-derived tag distinct: absent in older games (their tags stay), never read by the engine, not filled in by `fix_game_data`. The old game's versions and graph edges are untouched, and the `PARENT` relationship is never used for attribution. If saving fails, `parent`, `lineage`, title and author go back to what they were. Not offered during a live session.
- **Sprites and levels have stable IDs:** Every sprite and level carries a durable `id` (`src/static/game_ids.js`). `fix_game_data` fills in missing, invalid or duplicate IDs deterministically from the position (old games get `s0`, `s1`, … and `l0`, …) and never changes an existing valid ID. Editor actions that create a sprite or level must call `assign_new_game_id` before adding it, so a new object never inherits the ID of a deleted one. References to sprites are stored as sprite IDs: slot 0 of a placed sprite, `hit_sprite_id`/`attack_sprite_id`/`projectile_sprite_id` in attack visuals, `traits.baddie.drop.sprite_id` and `sprite_id` of `need_sprite` conditions. Old games hold indices in the legacy fields (`*_sprite_index`, `sprite_index`, slot 0); `fix_game_data` converts them, and an ID wins if both exist. The game engine keeps working with indices: `app.js` calls `resolve_sprite_references_to_indices` when it loads a game, which also drops references to sprites that no longer exist. The studio keeps unknown IDs until a sprite is deleted (`remove_sprite_references`), and the level editor drops placed sprites whose sprite is missing. Reordering sprites never rewrites references. Any new kind of sprite reference must be added to the walker in `game_ids.js`. State references inside one sprite (door states and the like) are still indices. A sprite may have a Titel (`properties.name`, like states and levels; `sprite_title`, `sprite_label`, `set_sprite_title` in `game_ids.js`): absent = none, and the editor calls it "Sprite N". It is never stored empty (`fix_game_data` does not add it, clearing it removes an empty `properties`), so old games save exactly as before; it is a label, not a reference. Everything that shows a sprite to choose (sprite list, the level editor's sprite buttons, `SpriteSelectWidget`, `SpriteWidget`) uses `sprite_label`; `Game.refresh_sprite_titles()` updates the hover titles after renaming, moving or deleting sprites and when a session participant renames one.
- **Sprites travel between games as copies** (`src/static/sprite_basket.js`, "Sprites holen": the basket tile next to + in the sprite list, or Funktionen → Sprite): a child picks from the **Sprite-Katalog** (a wide dialog: the source on the left – search and the groups as a list that marks the group in view, `mark_group_in_view`, or a game's code – and the sprites on the right; first tab: `/rezepte/katalog.json`, written by every recipe build from `rezepte/katalog.yaml` – every catalogue sprite in one game plus its groups (`sammlung`), shown grouped with a search over Titel and group name, `catalogue_groups`; recipe scenes are no longer listed one by one) or opens another game by its code (`/api/load_game`, second tab, unchanged), collects sprites in a basket (from several sources) and brings them in with all states, frames, traits and Titel. The source is normalized with `fix_game_data` first; `copy_sprites_for` gives the copies new IDs (`assign_new_game_id`) and points references among them at each other, and everything a chosen sprite refers to (`for_each_sprite_reference_in_sprite` in `game_ids.js`: attack visuals, projectile, drop) comes along ("kommt mit"). Nothing links the games afterwards, and placed settings stay with the levels. `Game.add_sprites` (game.js) is the one path for adding finished sprites (also used by Duplizieren, which inserts the copy right after its original); it calls `structure_changed` for each.
- **Signale connect senders and receivers by Code, within one level** (`src/static/signals.js`). Every Code is stored as `signal_code`: placed `key`/`door`/`switch`/`pressure_plate`/`baddie` properties, layer `properties`, `traits.baddie.drop`, and `level.properties.signal_all_defeated`. What a sprite *is* (key, Schalter, door, how a door opens) belongs to its drawing; what it is *connected to* belongs to each placed copy, so one drawing serves different connections. Hence the loot key of an enemy takes the placed `baddie.drop_code` (absent = the drawing's `traits.baddie.drop.signal_code`, the only Code older games have; `effective_loot_code`), and such an enemy counts as a sender in the editor (`placed_signal_roles`, role `loot`). A placed door may override its drawing's `lockable`/`automatic` (placed `door.lockable`/`door.automatic`, true or false; absent = as drawn; `door_setting`). Older games stored keys and doors (and loot) as `door_code` and had Sichtbarkeitsbereiche; `promote_legacy_signals` turns both into the new form, deterministically, in `fix_game_data` and when `app.js` loads a game (so old saved games play the same without being re-saved; a `signal_code` that is already there wins). Senders: a key when collected (an; it still sets `found_keys`), a Schalter (`switch`, only when the action key goes down), a Druckplatte (while the player's centre is above it), a Signalbereich (`signal_area` layer – the children see "Signalbereich" everywhere, so it is never confused with a Bewegungsbereich, which changes movement and sends nothing; older layers named "Bereich N" keep their names: an while the player's centre is in one of its rectangles, aus when it leaves; evaluated at once at level start and respawn, so a figure starting inside sees the right picture without a fade), a defeated enemy (placed `baddie.signal_on_defeat`, absent = sends nothing) and the level when no enemy is left (`signal_all_defeated`; enemies on a layer that is away do not count yet, so waves work, and enemies that are "unverwundbar" never count). Receivers decide what a signal means: a door by its placed `door_reaction` (absent = `unlock`, exactly the old key behaviour; the other reactions move the door themselves, also a locked one, and a door that is still moving does the last signal afterwards), and any sprite or backdrop layer by `properties.signal_code`/`signal_reaction`/`signal_fade` (absent = it does not react). A layer that is away is neither drawn nor collides, and its enemies wait (`signal_hidden`: no simulation, no contact damage, `CombatSystem.owner_is_alive` false). Its drawing fades over `signal_fade` seconds (default `SIGNAL_LAYER_FADE_SECONDS`) with its own material copies (`layer_fade.js`; enemies on it get theirs via `material_for_frame`); collisions switch at the moment of the signal. Every collision query goes through `Game.collision_candidates`; combat obstacle checks skip hidden entries too. Only the layer with the player never reacts. Every level starts with a new `SignalBus` in `setup()`; receivers keep their state when the player dies; a Schalter that starts *an* sends *aus* when first flipped; objects created later miss earlier signals; `SIGNAL_MAX_DEPTH` stops loops. Senders may send later (Verzögerung): placed `signal_delay` of a key, Schalter, Druckplatte or enemy, `properties.signal_delay` of a Signalbereich, `level.properties.signal_all_defeated_delay` (absent/0 = at once, at most `SIGNAL_DELAY_MAX_SECONDS`). Senders call `SignalBus.send`, which queues a delayed signal; `simulation_step` delivers what is due (`deliver_due`). Every signal arrives that much later, *an* and *aus* alike and in the order sent (an echo, not a timer that restarts); the sender's own picture (a Schalter's or Druckplatte's state) changes at once. Deciding at once (`signals.immediate`: level start, respawn, test start) ignores the Verzögerung and takes back what that sender still has on its way (`from`). A placed door may close again by itself (`door.close_after`, absent/0 = stays open; `door_auto_close_step`): the time counts from when it is fully open and starts again whenever it is asked to open while open (so an automatic door stays open while the figure stands in front of it); it closes doors whose drawing is not `closable`, too, and waits while the figure or an enemy overlaps the door. No door ever closes onto somebody: a door told to close by a signal while the figure or an enemy overlaps it (`Game.door_occupied`) keeps `door_signal_pending = 'close'` and waits in `doors_waiting_to_close` until the doorway is free (`update_waiting_doors`, every simulation step; a newer "open" signal takes it back, and "wechseln" counts the waiting door as closing), and the action key neither closes an occupied door nor shows its F hint (`toggle_door_intent`). This was an intentional bug fix: before, such a door closed onto the figure. New editor objects that send get a free Code (`free_signal_code`), so they never start something by accident: Signalbereiche, *alle Gegner besiegt*, newly placed Schalter and Druckplatten (`give_new_senders_codes`, pen and fill) and an enemy whose *sendet, wenn besiegt* is switched on without a Code (`give_defeat_sender_code`). Keys and doors still start on 0, where they have always met; a Code that is already there (also 0 typed in) is never replaced. The level editor draws connections from senders to receivers as animated dashes with marching frames (`LevelEditor.build_signal_links`, from `signal_objects`/`signal_links`): for the selection or the current layer, the overview card under the mouse and a Code clicked there (there is no "show all" toggle any more: the overview replaced "Verbindungen zeigen"). A delayed sender's lines carry a small "⏱ 1,5 s" label at the middle of their curve (`signal_object_delay` reads the stored `signal_delay`; `place_signal_link_labels` puts HTML labels over the view on every `render()`, since the curve bends with the zoom). The "Verbinden" tool (R) connects two things by clicking them (`pick_signal_object` looks for a sender first, then a receiver; `connect_signal_objects` keeps a Code that already links one of them to something else, never reuses 0, and gives the receiver a sensible reaction if it had none); it refuses to make a layer react to a sender that lies on that same layer. The Signale-Übersicht (S, also a checkbox under Werkzeuge and a status-bar toggle, remembered per browser) is a panel at the right edge of the level view with every Code of the level as a "Wenn … dann …" card (`signal_rules` in `signals.js`: senders and receivers as sentences with sprite labels and layer names, equal lines counted, Verzögerung, what "aus" does only where a receiver reacts to it, warnings for a Code nothing reacts to or nothing sends; plain doors – not verschließbar, *aufschließen* – are no receivers there). `LevelEditor.refresh_signal_overview` runs from `build_signal_links` and redraws only when the cards change; hovering a card shows only its Code's lines (`signal_focus_code`), clicking a line selects that object in its layer (`pick_signal_overview_object`), clicking the Code shows everything with it (`view_signal_rects`, which keeps the panel's part of the view free). Each line of a card has a × (`remove_signal_line`) that takes its objects out of the signal, and each card a trash can (`delete_signal_rule`) that does so for every line and removes the Code's name; both go through `clear_signal_object` (the same meaning as "Kein Signal"; the key an enemy leaves behind is left alone; locked layers refuse) and `signal_objects_cleared` (one undo step, every panel refreshed – the level settings' Signale boxes via `.level-signal-controls`). Rule objects carry the role id (`{ kind: 'sprite', …, role }`) and the level settings have objects too (`{ kind: 'level', setting }`), which are not selectable. Its last entry, "+ Neue Regel" (`start_new_signal_rule`), switches to the Verbinden tool and shows what to click. The panel stops mouse events, so the level view never paints or zooms through it. During "Level testen" (and only then, while the overview is switched on) the Spielen pane shows the same cards beside the game, read-only (`start_signal_watch`/`stop_signal_watch`, cards from `build_signal_card(…, false)`, which the overview uses too): the studio reads the game frame's `game.signals.sent` once per animation frame – the game itself does not change, and `app.js`/`signals.js` stay untouched (both are in the recipe build's engine fingerprint) – so a card flashes when its signal arrives (after any Verzögerung) and shows "an"/"aus"; a new bus (R) starts the cards afresh, another level (the exit was reached) dims them. `show_pane` stops the watch whenever the pane changes. A level may give its Codes names (`level.properties.signal_names`, e.g. `{ "4": "Brücke" }`; `signal_name`, `set_signal_name`, `signal_code_text` in `signals.js`): absent = numbers only, exactly as before; editor-only, never read by the game, never added by `fix_game_data`; the Code stays the number everywhere (bus, recipe checks, `free_signal_code`), so a typo in a name can never split a signal. Names are cleaned (`clean_signal_name`: trimmed, at most `SIGNAL_NAME_MAX_LENGTH` characters), two Codes of a level never share one (case-insensitive), removing the last name deletes `signal_names`, and a named Code counts as taken for `free_signal_code` even while nothing uses it, so a new sender never turns up with an old name. The overview cards (`card.name`) and the line under every Code (`describe_signal_partners(code, partners, name)`) show the name; a card is renamed in place (`add_signal_rule_name`, `rename_signal_code` in `level_editor.js`: the name or the pencil next to the Code becomes a field, Enter or blur saves, Esc cancels, a taken name gets a notice; it calls `history_observe`, so Strg+Z undoes it; `refresh_signal_overview` sets `signal_overview_rebuilding` while it removes the old panel so a field that vanishes does not save on blur). Every Code field in the level editor is a `SignalCodeWidget` (`level_editor.js`): the `NumberWidget` stays (typing a number works as before) and a button beside it shows the Code's name ("ohne Namen" without one) and lists the level's Codes with their names (0 only where something uses it), "Neues Signal …" (`free_signal_code`, then the name field) and "Namen geben …"; new Code fields should use it too. When the Verbinden tool creates a Code that the level did not use before, `ask_signal_name` shows a field over the level (beside the overview if it is open) with a suggestion from `unique_signal_name` ("Schalter → Gittertor", "… 2" when taken; labels from `signal_object_label`); Enter or blur saves through `rename_signal_code`, Esc leaves the Code unnamed. The level clipboard takes the names of its Codes along (`signal_names_for_placed`, stored as `level_clipboard.signal_names`), and pasting applies `carry_signal_names` to the pasted copies – the name wins: a name the target level already has → its Code; else the same number unnamed → it gets the name; else a free Code with the name; unnamed Codes keep their number; `signal_code` of every trait and `drop_code` are mapped once each (no swap chains). A drop key whose Code comes only from the drawing (no placed `drop_code`) is not remapped. Duplicating within a level and duplicating a whole level change nothing. "Kein Signal": an emptied Code field stores `signal_code: null` (key, door, Schalter, Druckplatte, Signalbereich) – that object neither sends nor reacts (`signal_key(null)` is null, so the bus ignores it; a key with null opens nothing) and leaves the overview and the lines. Absent still means 0, as always; older games never contain null, so they are unchanged. Read stored Codes through `stored_signal_code` (absent → 0, null → null), never `?? 0`; `Game.setup` keeps a stored null `signal_code` instead of the placed default. Things with their own switch are switched off instead: an enemy (`signal_on_defeat`), a sign (`speaks_on_signal`), a layer ("reagiert nicht") and the level settings. The `SignalCodeWidget` has its own input for this (an empty field is applied when it is left or with Enter, a number at once) and a "Kein Signal" menu entry; each use passes `clear` (the Beute has none: absent there means the drawing's Code). An enemy's Code and Verzögerung fields show only while "sendet, wenn besiegt" is on. Two more senders: any collected sprite with placed `pickup.signal_on_collect` (absent = sends nothing, as always; Code and Verzögerung as `pickup.signal_code`/`signal_delay`, shown only while it is on, a free Code when first switched on), and the level with `properties.signal_level_start` (+ `signal_level_start_delay`): once per level start (also R), never after a lost life; without a Verzögerung it is sent while the level decides at once, so the level looks right from its first frame, with one it is queued at time 0 on the level's clock (setup restarts the simulation at 0) as a timer that a respawn does not take back. A sprite that is key and pickup is a key in the editor (the pickup role comes last in `SIGNAL_SPRITE_ROLES`). In the game every placed setting of every trait lands on one flat entry, so the pickup's settings use `entry_key` (`pickup_signal_on`, `pickup_signal_code`, `pickup_signal_delay`) – any new placed setting that would clash with another trait's name needs one too. Two more receivers: a sign (`text` trait) with placed `text.speaks_on_signal` (absent = only with the action key, as always) speaks on "an" (`Game.signal_speech`, on the game clock because signals may arrive with time 0 while the level decides at once; a sign that is already speaking goes on; F still reads it), and the level with `properties.signal_level_complete` (absent = only the exit) is completed by "an" through `Game.complete_level(1, properties.signal_level_complete_target)` – the one path the exit (`level_complete` trait, placed `delta` and `target`, see "Levels are a sequence") uses too; it runs once per level (`reached_flag`). Do not let either be filled in by `fix_game_data`: placed defaults are never written. A Zähler (sprite trait `counter`; placed `counter.signal_code` = what it counts, `count` = Anzahl, absent 3, `send_code` = what it sends, `signal_delay`; game entry keys `counter_in`/`counter_count`/`counter_out`/`counter_delay`) is a receiver and a sender in one: "an" +1, "aus" −1, never below 0 (`counter_step`); reaching the Anzahl sends `send_code` "an", falling below sends "aus" (only on a change; `Game.counter_signal`), and it shows "Zähler zeigt n" / "erreicht" / "wartet" if drawn (`show_counter_state`). Its sending side is the role `SIGNAL_COUNTER_OUT_ROLE` (`counter_out`, like the loot role a second role of one placed sprite), so `pick_signal_object` offers it as a sender and its receiving side as a receiver, `set_signal_object_code` and `clear_signal_object` write `send_code` for it, `placed_signal_fields`/`signal_codes_in_level` know `send_code`, and a newly placed Zähler gets two free Codes (`give_new_senders_codes`). The exit (`level_complete`) is a receiver and a sender too, both optional (absent = as always: open, sends nothing): placed `level_complete.opens_on_signal` + `signal_code` (game entry keys `exit_gate_on`/`exit_gate_code`; `entry.exit_open` starts false and the first "an" of that Code opens it for good, shown with the state roles `level_complete: closed/open` – *Ausgang zu*/*Ausgang offen* – when drawn; a closed exit is skipped by the exit check) and placed `signal_on_reach` + `send_code` (`exit_send_on`/`exit_send_code`; `Game.exit_reached` sends "an" when the player starts touching an exit and "aus" when it stops, comparing entries by `entry_index` because `has_trait_at` returns copies). Its sending side is the role `SIGNAL_EXIT_OUT_ROLE` (`exit_out`, like `counter_out`), so Verbinden can connect switch → exit (it switches `opens_on_signal` on) and exit → anything (it switches `signal_on_reach` on); `clear_signal_object` switches them off again. The Signale-Übersicht always begins with the card **Level geschafft** (`level_complete_rule` in `level_map.js`, pure and tested: one line per exit – equal ones counted, with its target, *nur mit F*, its gate and whether it works – plus "geschafft bei Signal"; `problem: 'no_exit'` for a level without one). Its lines are interactive (`LevelEditor.build_complete_card`/`set_complete_line`): *→ weiter:* writes placed `target` (deleting an old `delta`) or `signal_level_complete_target`, *nur mit F* writes `action_key`, both one undo step; the test watch shows the card read-only. New senders and receivers connect to the same bus and use `signal_code` instead of adding a second linking system, and need a sentence in `signal_rules`; recipes check them end to end (`erwartet: signale`).
- **Sprechtexte are drawn into the game's canvas, never as HTML** (`src/static/speech.js`, `Game.draw_speech` in `app.js`): coloured pixel letters with a black outline (one font pixel) above the speaker, as a last render pass in screen pixels after the scene and the CRT pass – so they are crisp, unaffected by the CRT effect and visible in recipe recordings (`gl.readPixels`). They are sized to the screen, not the level: `speech_scale` picks a whole number of screen pixels per font pixel from the canvas height, and each line is rendered at its final size and thresholded to hard pixels. One font, size and reading speed per game (`data.properties.text_font`/`text_size`/`text_speed`, plus the figure's `text_color`; absent = the default, and choosing the default removes the field); four bundled OFL pixel fonts (`fonts/`, `SPEECH_FONTS` with their pixel grid and metrics). A sign (`text` trait) speaks its placed `text` as speech bubbles one after the other (`speech_parts`, `Speech`): with a `|` (`SPEECH_SEPARATOR`) anywhere in the text, the parts between `|` are the bubbles (line breaks inside are spaces; the level editor has a "Neue Sprechblase" button that inserts it); without one, every sentence is a bubble – split at line breaks and after . ! ? … when the next sentence begins (`split_sentences`: not after abbreviations, single letters or numbers, not before a lowercase word). No saved games used the older line rule; placed `speaker` is `player` (absent: the figure reads it out, in its colour) or `self` (above the sign, placed `color`). A sprite that speaks itself shows its state "spricht gerade" (state trait `text: speaking`) while its sentences are on screen and its earlier state afterwards (`Game.update_speaking_states`, before the animated sprites are drawn; absent = nothing changes) – the Wichtel of the recipe moves its mouth. The action key starts it on the moment it goes down and skips while somebody speaks; "." (`Period`, unless it is one of the game's own keys) and a tap skip, too; every other key plays on, and the game never pauses for text. `speech.log` lists every sentence shown (recipes: `erwartet: gesagt`). They may genuinely fail to traverse terrain; only after becoming lost do they recover near the player.** A companion is a third `Character` role (`character_trait === 'companion'`, sprite trait `traits.companion` = `vrun`, `can_fly`, `can_jump`, `vjump`, `can_swim`; only these child-level settings exist – distances, timers and the way back are constants in `COMPANION`, `src/static/companion_ai.js`, and are not exposed). It lives in `game.companions`, never in `game.baddies`, so combat targets, contact damage, `has_baddie_at`, "alle Gegner besiegt", drops and enemy signals never see it; it has no `energy` and never blocks the player. **A companion never acts on the level, because the player cannot control it:** it collects nothing, triggers no traps, Druckplatten, Signalbereiche, keys, Schalter, checkpoints or exits, holds no door open (`door_occupied` looks at the player and enemies only), does not make blocks fall (`falls_down`) and sends no signals. The level may act on it (gravity, slopes, conveyors, Bewegungsbereiche); new features must keep this one-way. Do not implement anything companion-like as a harmless enemy. `companion_decide` (pure, like `baddie_decide`) chooses virtual keys from what `Character.companion_perception` reports – its own `can_jump_over` and jump distance, never the player's; the movement is the shared `Character.simulation_step` (gravity, slopes, conveyors, Bewegungsbereiche, animation). The runtime traits are a copy (`this.traits`), the saved trait is never changed. Following uses hysteresis (`STOP`/`FOLLOW`) and a slot per companion (`companion_slot`, walkers and flyers counted separately) so several line up; a flyer (`ai_no_gravity`, `ai_dy`) heads for a spot behind and above the player and ignores Bewegungsbereiche; a companion that cannot swim treats water as no Bewegungsbereich and its AI stops at the shore; a swimmer leaps out with a stroke (`near_surface`) as high as its own Sprungkraft. `companion_lost_step`: lost only when far (`LOST_FAR`), out of the camera's view and without progress for `STUCK_SECONDS` (or fallen out of the level); it returns `RETURN_DELAY` later (`Character.return_to_player`: just outside the view, behind the player first, at the player's height, on ground / in the player's water / in the air; otherwise right beside the player). On the player's respawn every companion is put beside it at once. A placed companion may wait for a signal (placed `companion.waits_for_signal` + `signal_code`, absent = follows from the start; `Character.companion_waiting`): it presses nothing, hovers if it flies, looks at the player when it is near, is never lost and is not moved on respawn, until "an" arrives – then it follows for good (receiver role `companion` in `SIGNAL_SPRITE_ROLES`, sentence "kommt »…« mit"). That is the level acting on the companion; the companion still never sends anything. Keeping busy (`COMPANION_IDLE`, `companion_idle_ready`/`companion_idle_walk`/`companion_idle_fly`, pure and tested): once the player has stood still for `START` seconds and is near, a walker strolls a few steps on its own side of the player, sits down or sniffs/pecks (output `pose`: `sit`/`busy`, shown via `ai_pose` only if the sprite has the optional states *Begleiter sitzt* / *beschäftigt sich* – `sit_*`/`busy_*`), a flyer flutters from spot to spot around the player, lands (gravity on: on the ground it shows its Stehen/Laufen pictures, hops – only with a drawn walk picture: `has_pose` counts only drawn movement states, confidence 100, because walk always falls back to the standing picture –, pecks) and flies up again; it stops as soon as the player moves. A waiting companion does the same around its own place while the player is farther than six blocks. It uses its own little random sequence (`companion_random`, a seed in its memory), never Math.random, so recipe recordings and checks are repeatable. Recipes check companions with `begleiter_*` (also `begleiter_zeigt: [sit, busy]` and `begleiter_landet`) and `begleiter_einzeln` (by sprite Titel) in `erwartet` (`rezepte/tools/record.mjs`). There is one companion recipe (*Ein Begleiter kommt mit*: the dog, and the robot, bird and kitten as variant recordings in its text, one companion per recording, two of them about keeping busy); its scene carries every catalogue companion (`szene.zusaetzlich`), so the sprite basket offers them all. Pictures never decide abilities: "Begleiter fliegt" is only shown when `can_fly` is on.
- **Moving platforms and lifts carry, never push** (`src/static/platforms.js`, sprite trait `moving` with drawing-level `speed`/`pause`; placed `moving.path_x`/`path_y` (pixels, + right/up; absent = 96/0), `start` (`always` | `ride` | `signal`, absent = `always`) and `signal_code` – placed defaults are never written, and `start`/`signal_code` land on the game entry as `platform_start`/`platform_code` (`entry_key`)). `platform_plan` is pure (distance along the Weg in pixels, so whole-pixel speeds stay exact); `MovingPlatforms.setup` makes `game.moving_platforms` in `Game.setup` (only sprites in layers with collisions and no Parallaxe are level entries, so only they move), and `MovingPlatforms.step` runs first in `Game.simulation_step`: it moves the entry and its interval-tree intervals (always computed from the mesh position, so pickups, `falls_down` and doors that remove an entry still find it), then carries riders – figures whose feet stand on its top (`block_above`) and are not also standing on something that does not move, plus, when rising, figures whose feet it passes – sideways with `try_move_x` and vertically onto its top. It waits instead of moving when a solid platform (`block_sides`/`block_below`) would run into a figure not riding it, or when a rider's head would hit a `block_below` ceiling; nobody is ever squashed. A collected, falling or hidden entry rests. Only the player starts a lift (`ride`): companions and enemies ride along but never act on it. "bei Signal" is a receiver role (`SIGNAL_SPRITE_ROLES`, active only with `start: 'signal'`; the Verbinden tool sets it; "an" → end, "aus" → back) with a sentence in `signal_rules`. The level editor draws every Weg as a dashed line with a dashed frame at the end (`LevelEditor.build_platform_paths`, rebuilt with the signal links and on every change of a placed `moving` setting); with the select tool and one platform selected, a round handle in that frame drags the end (`place_platform_handle`, placed on every `render()`; `start_platform_drag` snaps the end like the pen, `sprite_grid_point`, Shift pixel by pixel, and writes `path_x`/`path_y`; the level history makes it one undo step). Recipes check `plattform_weg`, `figur_mitgefahren` and `plattform_wartet`. `platforms.js` and `app.js` are in the recipe build's engine fingerprint.
- **Levels are a sequence unless a child chooses otherwise** (`src/static/level_flow.js`, pure and tested; `Game.complete_level(delta, target)` and `place_player_on_arrival` in `app.js`). An exit (`level_complete`) has placed `target` (game entry `exit_target`; absent = the next level in use, by its placed `delta`, exactly as before), a level id, `'@back'` or `'@end'`; and placed `action_key` (`exit_action_key`; absent = on touch, as always; true = the F hint and a fresh press of the action key, never one still held from the level before – `Game.keys_down`/`action_key_held`, because `setup()` forgets `pressed_keys`). `level.properties.side_level` (absent = part of the order) makes a Nebenlevel: `next_level_in_sequence` skips it like an unused level, and its exits without a target mean `'@back'`. `level.properties.signal_level_complete_target` is the same choice for "geschafft bei Signal". "zurück" follows `game.level_trail` (ids of the levels the player came from; going back pops, going to a level already in it cuts it there, at most `LEVEL_TRAIL_MAX`); with nothing to go back to (a test run started in the shop) it is the next level. A level entered through a chosen target puts the player on the exit that leads back to the level it came from (`arrival_exit_index`: exactly that level first, then `'@back'`), as its respawn point too, and brings non-waiting companions along; exits without a target never count, so old games start where they always did. No exit works until the player has once touched none (`exit_armed`), so arriving on one never sends it straight back. A game starts with `first_level_index` (the first level in use that is no Nebenlevel – before, an unused first level was played anyway: an intentional fix), and lives and energy are set by `reset()` only (before, `setup()` refilled them whenever level 0 was set up, which a hub at the front would have done on every visit: an intentional fix; only games that jumped back to level 0 with a negative Delta notice it). Targets are level ids, never indices: reordering levels changes nothing, a deleted target behaves like no target, and the editor keeps showing it ("ein Level, das es nicht mehr gibt") instead of changing the stored value. `fix_game_data` writes none of these fields. The editor's "führt zu" is a placed property of type `level_target` (`LevelEditor.level_target_choices`); choosing "zum nächsten Level" deletes `target`. "führt zu" replaced the Delta field: the game still reads placed `delta` (older games, absent = 1), the editor no longer shows it, and an exit whose Delta is not 1 lists it as its own choice ("»Level 4« (1 Level überspringen, von früher)", value `LEVEL_TARGET_DELTA`, never stored) until another choice deletes `delta`. Placed property `visible(traits, traits_of, props, level)` gets the level as a fourth argument.
- **The Levelübersicht is computed, never stored** (`src/static/level_map.js`, pure and tested; `LevelEditor.refresh_level_map`, L, a view option like G/S/M/A but not remembered per browser, because it covers the level). `level_map_exits` finds exits exactly as the game does (only layers with Kollisionen and Parallaxe 0 work; others are listed with a warning) plus "geschafft bei Signal"; `level_map` resolves them with `level_flow.js` into edges `next` / `target` / `back` (a "zurück" exit points to every level that leads in) / `end`, places levels in columns by their shortest distance from the first level and rows in list order (unreachable ones in a last row), and writes German warnings (never reached, Nebenlevel without a way in, "zurück" from nowhere, a deleted or unused target, a broken layer; none for unused levels, which are drafts). A level without an exit is no warning but a hint (`node.hints`, "Noch kein Ausgang"): if it is in the order, an edge of kind `order` leads to `next_level_in_sequence` (or the end), drawn thin and dashed (*Reihenfolge*), so a new game – one level, no exit – is connected and its end reachable; clicking such an edge opens the level and explains how to make an exit, and a help line under the map says where an exit's target is set. The editor draws plain nodes (name, start, Nebenlevel, number of warnings – no level pictures, on purpose) and SVG arrows; it is rebuilt from `build_signal_links` and `update_level_label` only when the computed map changes, scales itself down to fit, and clicking a node calls `levels_widget.select_index`, clicking an arrow selects its exit through `pick_signal_overview_object`. What opens an exit is `exit.gate` (`level_map_gate`): "geschafft bei Signal", or an exit on a layer that reacts to a Code (`layer_reacts_to_signals`; `closed` when the layer starts away, `layer_visible_at_start`), with the Code's name and its senders (`level_map_senders` from `signal_partners`, using the globals of `signals.js` when they are loaded – the tests load them); a closed gate whose Code nothing sends is a warning. The arrow gets ⚡ and the gate texts in its title (`.level-map-badge.never` in red). Doors are deliberately not linked to exits (only placement relates them). `level_map.js` is editor-only, so none of this touches the engine fingerprint.
- **A level entered again remembers what happened in it** (during one run: `Game.level_memory`, level id → `{ gone, defeated, switches, drops, sends }`; cleared by `reset()`, so a new game, game over → Start and every test run start afresh). Placed entries and enemies carry `place` (`"<layer index>:<index in layer>"`). Remembered: collected sprites and keys (`remember_collected`; a remembered key sets `found_keys` again), defeated enemies (`remember_defeated`; they are left out on re-entry) and their uncollected loot (respawned where it lay, `drop_of`), each Schalter's position, and every signal those senders sent, in order (`remember_send`, at most `LEVEL_MEMORY_MAX_SENDS`): the keys', "sendet, wenn eingesammelt", Schalter, "sendet, wenn besiegt" and "alle Gegner besiegt". `restore_level_memory` runs in `setup()` before the arrival and the signals; `replay_level_memory` at the end of `setup_signals` sends the remembered signals again with `signals.immediate` (no Verzögerung), while `replaying_memory` keeps them from completing the level or making a sign speak and from being remembered twice; companions found that way come along. Not remembered, on purpose: falling blocks (a crumbled bridge must come back, or a level could become impossible), Druckplatten, Signalbereiche, "sendet beim Start" (it starts again), checkpoints and doors opened with F. A level is only entered again through exits with targets or a negative Delta, so plain sequences never see this. New senders whose effect should last must call `remember_send` too.
- **The HUD is drawn, not HTML, and shows only what a game uses** (`src/static/hud.js`, pure parts tested; `Game.setup_hud`/`draw_hud` in `app.js`; the old `#stats` bar with Level / Punkte / Leben / Energie is gone, `update_stats` is an empty hook). `hud_plan(data)` decides once per game: hearts if `lives_at_begin` > 1 or a pickup gives lives, the energy bar if `show_energy` and a sprite is a trap or an enemy or gives energy, the counter if a pickup gives points; the pictures are the most-placed sprite that gives lives / points (`hud_icon_pixels`: cut to what is drawn, halved above `HUD.ICON_MAX`, a one-pixel `HUD.INK` outline; a lost heart is the same picture in `HUD.EMPTY`), taken from the sprite sheet (4× in the sheet). One HUD pixel is `hud_scale` screen pixels (the game's pixel size, kept between 2.5 % and 4.5 % of the screen height for the font's capitals); the canvas is as wide as the screen and `HUD.STRIP` HUD pixels tall, drawn after the scene and the CRT pass and before the speech (`draw_hud`), and uploaded only when `HudPainter.paint` returns a new key. Text uses the game's speech font through `render_speech_bitmap` at k screen pixels per font pixel (one pixel per font pixel breaks a pixel font), and is drawn again when the font has loaded. Animations run on the level's clock; `setup()` keeps the painter for the same game and only resets the level name. `game.hud_off` hides it (the recipe recorder sets it, because a recording shows part of the level, not the screen). Points are what the counter counts – they are the game's currency now; a separate inventory is still open (TODO).
- **The F hint stands in front of its layer, behind the figure** (`Game.place_overlay_meshes`, called in `setup()` before the arrival): the hint mesh lies at z 0 like the sprites, and because the scene is drawn in order (`renderer.sortObjects = false`), it is moved to just before the player's mesh in the player's group (in front of every sprite of that layer, behind the figure), or to the end of its own group in other layers. Anything that adds hint meshes must call it again.

- `src/static/hud.js`: the HUD – what a game shows (hearts, energy, its coin counter, the level's name) and how it is painted.
- `src/static/speech.js`: Sprechtexte – fonts, settings, sentences, timing, wrapping and the pixel rasterizer (the render pass is `Game.draw_speech` in `app.js`).
- `src/static/signals.js`: Signale – the per-level bus, door and layer reactions, and the editor's "what else has this Code" line.
- `src/static/companion_ai.js`: Begleiter – the decisions of a companion (following, its own jumps, swimming, flying, lost and found); the runtime role is `Character` in `app.js` (`simulate_companion`, `companion_perception`, `update_companion_lost`, `return_to_player`).
- `src/static/level_flow.js`: which level comes next – exit targets, Nebenlevel, "zurück" and where the player arrives (shared by `app.js` and the level editor).
- `src/static/level_map.js`: the Levelübersicht – how the levels are connected, laid out, with warnings and what opens an exit (editor only).
- `src/static/level_list_history.js`: undo/redo of new, duplicated, deleted and moved levels.
- `src/static/who_shows_what.js`: Wer zeigt was? – `figure_state_table` rebuilds the game's `Character.sti_for_state` (app.js) without the engine, `who_shows_what` classifies each role and direction (drawn, mirrored, other, base – the Grundbild; nothing is called missing or wrong: one picture for everything is a working figure, the panel shows room for more, "Platz für N Bilder"), `object_state_roles` the states of doors, switches, counters …, and the panel in `#who_shows_what` (refreshed from `build_state_traits_menu`, pictures from `refresh_frames_on_screen`). `test/who_shows_what.test.cjs` compares the table with the real `Character` for hundreds of random sprites – change both together if the game's choice of states changes.
- `src/static/platforms.js`: Bewegte Plattformen und Aufzüge – the plan of each platform and the step that moves it and carries riders.
- `src/static/movement_regions.js`: opt-in Bewegungsbereiche (swim, float, other gravity, currents) for the player character and walking enemies, per rectangle layer or for the whole level.
- `src/static/combat.js`, `src/static/combat_swing.js`, `src/static/combat_projectile.js`, `src/static/combat_melee_trait.js`: shared attack, melee, projectile/bomb deliveries and legacy/new trait adapters.
- `src/static/playtesting.js`, `src/ruby/playtesting.rb`, `src/ruby/playtest.rb`, `src/ruby/playtest_pdf.rb`: playtesting in class (the tab, the rules and state, the teacher's script, the printed feedback).
- `src/ruby/errors.rb`: the teacher's script for the studio's Fehlerberichte (`client_errors.rb`).
- `rezepte/`: German how-to recipes for the Hilfe tab. `rezepte/tools/build.mjs` records each recipe's GIF from the real engine in headless Chromium, checks the recipe's promised outcome and writes `src/static/rezepte/` (commit the generated files). Rebuild after gameplay changes; a failing recipe means children would be told something that no longer works. See `rezepte/README.md`. The build also writes every recipe's scene as an openable game (`spiele/<id>.json`, `spiel` in `rezepte.json`); the Hilfe tab opens it in the studio (`rezepte.js`) with `game.from_recipe` set, and `Game.save` then asks for an own title and author instead of saving the recipe (own_game.js, mode `recipe`). `from_recipe` is session-only, cleared by every `_load`, and live sessions refuse to start from a recipe scene.
- `rezepte/anleitungen/`, `rezepte/tools/anleitungen.mjs` (+ `anleitung.mjs`, `film.mjs`, `studio.mjs`; played by `src/static/anleitung_film.js`): the Erste-Schritte guides, recorded from the real `studio.html` with stubbed API (see `rezepte/README.md`). Their fingerprint covers all of `src/static`, so any studio change records them again (`npm run anleitungen`, about two minutes per guide); a guide whose selector no longer matches fails. When a label, title or button a guide uses changes, adjust the guide's steps in the same patch. Commit `src/static/anleitungen/`.
