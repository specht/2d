# 2D Game Studio — notes for future development sessions

Read `TODO.md` and inspect the current repository before proposing changes. This is a visual game-making tool used by children, and hundreds of existing games have been saved. The TODO is a collection of ideas and reports, **not** a list of verified bugs or approved feature designs.

## Working agreement

- **Advice and patches only.** Never push to GitHub, create remote branches or pull requests, commit changes, or modify this repository on the user's behalf. Provide a patch based on the current branch for the user to inspect and apply locally. Do not assume a previous patch or this file has been applied.
- **Saved JSON is a compatibility contract.** Old game descriptions must load unchanged. Preserve existing trait/state/property names, array layouts, defaults, references, and the meaning of absent fields. Do not require users to migrate or re-export games. New features should use optional fields with legacy-compatible defaults. When modernizing mechanics, prefer a runtime compatibility adapter over rewriting stored JSON; keep legacy semantics and define explicit precedence if old and new fields coexist. Compatibility is one-way: saving may write a newer format, because only the current code reads saved games. `fix_game_data` must stay deterministic (the same JSON always normalizes to the same result), since content-derived tags and recipe fingerprints depend on it.
- **Preserve established gameplay.** Runtime internals may change, but assess any visible change to old games. Identify an intentional bug fix and its compatibility implications instead of silently changing existing behavior. Do not enable formerly ignored level-completion conditions for old games without a compatibility strategy.
- **Small, focused patches.** Implement one agreed issue or milestone at a time, explain the change and give practical checks for existing and new games. Add focused automated tests where they help; never substitute isolated tests for browser/gameplay verification.
- Keep the visual trait-based editor approachable. Separate **control**, **movement/physics**, **abilities** and **presentation** where practical; combine capabilities through traits instead of hardcoding platformer-only character classes. Do not begin a wholesale ECS/physics rewrite.

## Established behavior and design boundaries

- **Seamless interiors are built with Signale:** a Bereich over the house sends its Code while the player's centre is inside, and the facade/roof layer reacts with "weg, solange an" (optionally fading). There is no separate visibility system any more: old Sichtbarkeitsbereiche (`visibility_region` layers) are promoted to Bereiche on load (see Signale). Facade/roof art should have collision disabled, because a layer that is away also does not collide.
- **Combat foundation is implemented:** Shared actor/baddie melee, ranged projectiles and timed bombs; preserve legacy attacks and J/K/F controls. New attack families must use the same owner-neutral combat machinery for actor and baddie from their first playable version rather than creating a second enemy-only or player-only damage system.
- **Unverwundbare Gegner:** `traits.baddie.invincible` (drawing-level, default false): `Character.take_damage` ignores all damage for it (combat, falling blocks, anything added later) and `CombatSystem.apply_hit` refuses the hit before any damage or hit effect; a projectile still stops at it. Its own attacks and contact damage are unchanged. New damage sources must go through `take_damage` or `apply_hit` so this keeps holding.
- **Combat rules are independent of artwork:** Delivery, targeting, damage, timing and hit geometry come from combat configuration and runtime state, never from image pixels, frame count or sprite colour. Optional attack/hit/death animation states are presentation and must not silently change damage or collision semantics. Projectiles and other attack visuals likewise do not inherit unrelated placed-sprite traits.
- **Future combat stays incremental:** Instant lasers/rays, reusable area attacks, cooldown feedback and finite ammunition remain separate backlog items. A continuous beam is a distinct mechanic from an instant ray because it needs explicit re-hit/interrupt timing.
- **Collaboration is explicit and capability-by-link:** Do not introduce accounts, ownership or private-game permissions just to support live collaboration. A normal public game code may continue to let anybody open and save a descendant, but joining an active shared editing session requires its own hard-to-guess temporary session link/code. Every participant supplies a session-local display name; use it for presence and lock/conflict messages, but never treat it as authentication or durable ownership metadata. Address sprites and levels by their durable `id`, never by array index; keep session-only metadata (participants, locks, revisions) out of saved JSON. Prefer server-authoritative revisions and small resource leases/locks for the first implementation over a wholesale CRDT rewrite. The server never interprets references between resources; every editor action that adds, deletes or moves a sprite or level must call `window.collaboration?.structure_changed(kind, action, id)` after changing the local list (and lists offer `can_delete_index` so a locked item cannot be deleted). Anything that replaces the studio's game with another one must not do so silently during a session: `game.load()` is already guarded, other paths call `window.collaboration.confirm_leave('load', proceed)` first. Switching between sprites or levels must not flash or dim the editor: a resource is editable at once unless somebody else holds its lock; the client keeps the last server-confirmed value of every resource (`server_values`), sends what differs once its lock arrives, and undoes it if somebody else was faster. Showing a sprite must not change its data (the canvas does not re-encode a frame it only displays). Participant colours are indices handed out by the server (`COLOR_COUNT` in `collaboration.rb`) and mapped to `COLLABORATION_COLORS` in `collaboration.js`; keep both lengths equal. Shared saves must still go through the established immutable game/version path. `raw/collaboration/sessions.json` holds session codes and reconnect tokens: never move it below `gen/` or anywhere else nginx serves.
- **Als eigenes Spiel weiterführen starts a new game, never edits the old one** (`src/static/own_game.js`, Einstellungen → Spiel): after asking for a new title and the author, the current state is saved with `parent: null` and a fresh random top-level `lineage`, so it becomes a root (a new entry in the game list) with its own code even if nothing changed; later saves descend from it. `lineage` exists only to make the content-derived tag distinct: absent in older games (their tags stay), never read by the engine, not filled in by `fix_game_data`. The old game's versions and graph edges are untouched, and the `PARENT` relationship is never used for attribution. If saving fails, `parent`, `lineage`, title and author go back to what they were. Not offered during a live session.
- **Sprites and levels have stable IDs:** Every sprite and level carries a durable `id` (`src/static/game_ids.js`). `fix_game_data` fills in missing, invalid or duplicate IDs deterministically from the position (old games get `s0`, `s1`, … and `l0`, …) and never changes an existing valid ID. Editor actions that create a sprite or level must call `assign_new_game_id` before adding it, so a new object never inherits the ID of a deleted one. References to sprites are stored as sprite IDs: slot 0 of a placed sprite, `hit_sprite_id`/`attack_sprite_id`/`projectile_sprite_id` in attack visuals, `traits.baddie.drop.sprite_id` and `sprite_id` of `need_sprite` conditions. Old games hold indices in the legacy fields (`*_sprite_index`, `sprite_index`, slot 0); `fix_game_data` converts them, and an ID wins if both exist. The game engine keeps working with indices: `app.js` calls `resolve_sprite_references_to_indices` when it loads a game, which also drops references to sprites that no longer exist. The studio keeps unknown IDs until a sprite is deleted (`remove_sprite_references`), and the level editor drops placed sprites whose sprite is missing. Reordering sprites never rewrites references. Any new kind of sprite reference must be added to the walker in `game_ids.js`. State references inside one sprite (door states and the like) are still indices. A sprite may have a Titel (`properties.name`, like states and levels; `sprite_title`, `sprite_label`, `set_sprite_title` in `game_ids.js`): absent = none, and the editor calls it "Sprite N". It is never stored empty (`fix_game_data` does not add it, clearing it removes an empty `properties`), so old games save exactly as before; it is a label, not a reference. Everything that shows a sprite to choose (sprite list, the level editor's sprite buttons, `SpriteSelectWidget`, `SpriteWidget`) uses `sprite_label`; `Game.refresh_sprite_titles()` updates the hover titles after renaming, moving or deleting sprites and when a session participant renames one.
- **Sprites travel between games as copies** (`src/static/sprite_basket.js`, the basket tile next to + in the sprite list, or Funktionen → Sprite): a child opens another game by its code (`/api/load_game`) or a recipe scene, collects sprites in a basket (from several games) and brings them in with all states, frames, traits and Titel. The source is normalized with `fix_game_data` first; `copy_sprites_for` gives the copies new IDs (`assign_new_game_id`) and points references among them at each other, and everything a chosen sprite refers to (`for_each_sprite_reference_in_sprite` in `game_ids.js`: attack visuals, projectile, drop) comes along ("kommt mit"). Nothing links the games afterwards, and placed settings stay with the levels. `Game.add_sprites` (game.js) is the one path for adding finished sprites (also used by Duplizieren, which inserts the copy right after its original); it calls `structure_changed` for each.
- **Signale connect senders and receivers by Code, within one level** (`src/static/signals.js`). Every Code is stored as `signal_code`: placed `key`/`door`/`switch`/`pressure_plate`/`baddie` properties, layer `properties`, `traits.baddie.drop`, and `level.properties.signal_all_defeated`. What a sprite *is* (key, Schalter, door, how a door opens) belongs to its drawing; what it is *connected to* belongs to each placed copy, so one drawing serves different connections. Hence the loot key of an enemy takes the placed `baddie.drop_code` (absent = the drawing's `traits.baddie.drop.signal_code`, the only Code older games have; `effective_loot_code`), and such an enemy counts as a sender in the editor (`placed_signal_roles`, role `loot`). A placed door may override its drawing's `lockable`/`automatic` (placed `door.lockable`/`door.automatic`, true or false; absent = as drawn; `door_setting`). Older games stored keys and doors (and loot) as `door_code` and had Sichtbarkeitsbereiche; `promote_legacy_signals` turns both into the new form, deterministically, in `fix_game_data` and when `app.js` loads a game (so old saved games play the same without being re-saved; a `signal_code` that is already there wins). Senders: a key when collected (an; it still sets `found_keys`), a Schalter (`switch`, only when the action key goes down), a Druckplatte (while the player's centre is above it), a Bereich (`signal_area` layer: an while the player's centre is in one of its rectangles, aus when it leaves; evaluated at once at level start and respawn, so a figure starting inside sees the right picture without a fade), a defeated enemy (placed `baddie.signal_on_defeat`, absent = sends nothing) and the level when no enemy is left (`signal_all_defeated`; enemies on a layer that is away do not count yet, so waves work, and enemies that are "unverwundbar" never count). Receivers decide what a signal means: a door by its placed `door_reaction` (absent = `unlock`, exactly the old key behaviour; the other reactions move the door themselves, also a locked one, and a door that is still moving does the last signal afterwards), and any sprite or backdrop layer by `properties.signal_code`/`signal_reaction`/`signal_fade` (absent = it does not react). A layer that is away is neither drawn nor collides, and its enemies wait (`signal_hidden`: no simulation, no contact damage, `CombatSystem.owner_is_alive` false). Its drawing fades over `signal_fade` seconds (default `SIGNAL_LAYER_FADE_SECONDS`) with its own material copies (`layer_fade.js`; enemies on it get theirs via `material_for_frame`); collisions switch at the moment of the signal. Every collision query goes through `Game.collision_candidates`; combat obstacle checks skip hidden entries too. Only the layer with the player never reacts. Every level starts with a new `SignalBus` in `setup()`; receivers keep their state when the player dies; a Schalter that starts *an* sends *aus* when first flipped; objects created later miss earlier signals; `SIGNAL_MAX_DEPTH` stops loops. Senders may send later (Verzögerung): placed `signal_delay` of a key, Schalter, Druckplatte or enemy, `properties.signal_delay` of a Bereich, `level.properties.signal_all_defeated_delay` (absent/0 = at once, at most `SIGNAL_DELAY_MAX_SECONDS`). Senders call `SignalBus.send`, which queues a delayed signal; `simulation_step` delivers what is due (`deliver_due`). Every signal arrives that much later, *an* and *aus* alike and in the order sent (an echo, not a timer that restarts); the sender's own picture (a Schalter's or Druckplatte's state) changes at once. Deciding at once (`signals.immediate`: level start, respawn, test start) ignores the Verzögerung and takes back what that sender still has on its way (`from`). A placed door may close again by itself (`door.close_after`, absent/0 = stays open; `door_auto_close_step`): the time counts from when it is fully open and starts again whenever it is asked to open while open (so an automatic door stays open while the figure stands in front of it); it closes doors whose drawing is not `closable`, too, and waits while the figure or an enemy overlaps the door. A door closed by a signal or the action key still does not wait. New editor objects that send get a free Code (`free_signal_code`), so they never start something by accident: Bereiche, *alle Gegner besiegt*, newly placed Schalter and Druckplatten (`give_new_senders_codes`, pen and fill) and an enemy whose *sendet, wenn besiegt* is switched on without a Code (`give_defeat_sender_code`). Keys and doors still start on 0, where they have always met; a Code that is already there (also 0 typed in) is never replaced. The level editor draws connections from senders to receivers as animated dashes with marching frames (`LevelEditor.build_signal_links`, from `signal_objects`/`signal_links`): for the selection or the current layer, or all of them with "Verbindungen zeigen". The "Verbinden" tool (R) connects two things by clicking them (`pick_signal_object` looks for a sender first, then a receiver; `connect_signal_objects` keeps a Code that already links one of them to something else, never reuses 0, and gives the receiver a sensible reaction if it had none); it refuses to make a layer react to a sender that lies on that same layer. The Signale-Übersicht (S, also a checkbox under Werkzeuge and a status-bar toggle, remembered per browser) is a panel at the right edge of the level view with every Code of the level as a "Wenn … dann …" card (`signal_rules` in `signals.js`: senders and receivers as sentences with sprite labels and layer names, equal lines counted, Verzögerung, what "aus" does only where a receiver reacts to it, warnings for a Code nothing reacts to or nothing sends; plain doors – not verschließbar, *aufschließen* – are no receivers there). `LevelEditor.refresh_signal_overview` runs from `build_signal_links` and redraws only when the cards change; hovering a card shows only its Code's lines (`signal_focus_code`), clicking a line selects that object in its layer (`pick_signal_overview_object`), clicking the Code shows everything with it (`view_signal_rects`, which keeps the panel's part of the view free). The panel stops mouse events, so the level view never paints or zooms through it. A level may give its Codes names (`level.properties.signal_names`, e.g. `{ "4": "Brücke" }`; `signal_name`, `set_signal_name`, `signal_code_text` in `signals.js`): absent = numbers only, exactly as before; editor-only, never read by the game, never added by `fix_game_data`; the Code stays the number everywhere (bus, recipe checks, `free_signal_code`), so a typo in a name can never split a signal. Names are cleaned (`clean_signal_name`: trimmed, at most `SIGNAL_NAME_MAX_LENGTH` characters), two Codes of a level never share one (case-insensitive), removing the last name deletes `signal_names`, and a named Code counts as taken for `free_signal_code` even while nothing uses it, so a new sender never turns up with an old name. The overview cards (`card.name`) and the line under every Code (`describe_signal_partners(code, partners, name)`) show the name. New senders and receivers connect to the same bus and use `signal_code` instead of adding a second linking system, and need a sentence in `signal_rules`; recipes check them end to end (`erwartet: signale`).
- **Sprechtexte are drawn into the game's canvas, never as HTML** (`src/static/speech.js`, `Game.draw_speech` in `app.js`): coloured pixel letters with a black outline (one font pixel) above the speaker, as a last render pass in screen pixels after the scene and the CRT pass – so they are crisp, unaffected by the CRT effect and visible in recipe recordings (`gl.readPixels`). They are sized to the screen, not the level: `speech_scale` picks a whole number of screen pixels per font pixel from the canvas height, and each line is rendered at its final size and thresholded to hard pixels. One font, size and reading speed per game (`data.properties.text_font`/`text_size`/`text_speed`, plus the figure's `text_color`; absent = the default, and choosing the default removes the field); four bundled OFL pixel fonts (`fonts/`, `SPEECH_FONTS` with their pixel grid and metrics). A sign (`text` trait) speaks its placed `text` as speech bubbles one after the other (`speech_parts`, `Speech`): with a `|` (`SPEECH_SEPARATOR`) anywhere in the text, the parts between `|` are the bubbles (line breaks inside are spaces; the level editor has a "Neue Sprechblase" button that inserts it); without one, every sentence is a bubble – split at line breaks and after . ! ? … when the next sentence begins (`split_sentences`: not after abbreviations, single letters or numbers, not before a lowercase word). No saved games used the older line rule; placed `speaker` is `player` (absent: the figure reads it out, in its colour) or `self` (above the sign, placed `color`). The action key starts it on the moment it goes down and skips while somebody speaks; "." (`Period`, unless it is one of the game's own keys) and a tap skip, too; every other key plays on, and the game never pauses for text. `speech.log` lists every sentence shown (recipes: `erwartet: gesagt`). Plain sprites only: enemies and the figure are not level entries and cannot carry a `text` trait that speaks.
- **Right-click menus duplicate and move things around** (`show_context_menu` in `widgets.js`; a list gets one with the `DragAndDropWidget` option `context_menu(index)`). Sprite editor (`src/static/sprite_actions.js`): sprites (Duplizieren), states (Duplizieren, Animation kopieren, Frames einfügen, Animation tauschen mit, In anderes Sprite kopieren) and frames (Duplizieren, Kopieren, Ausschneiden, Einfügen, In anderen Zustand verschieben); the frame clipboard lives as long as the page and only pastes into sprites of the same size. States are referred to by their position in a sprite, so a new or copied state always goes to the end and nothing here reorders states; a duplicated state takes no role (its state traits are emptied), a state copied into another sprite keeps the roles of the traits that sprite has. Level editor: levels and layers (Duplizieren, right after the original) and the sprite palette (Im Sprite-Editor bearbeiten, Alle in dieser Ebene auswählen, Duplizieren). Structural changes in the sprite editor have no undo (like dragging to the trash); level and layer changes are caught by the level history as usual.
- **Dropdowns look like the right-click menus** (`enhance_select` in `widgets.js`): every `<select>` in the studio is enhanced automatically (a MutationObserver finds new ones) into a button that opens a `show_context_menu` list; the `<select>` stays in the page, hidden, so its value, options, `disabled` and `change` event work as before, and values set from code update the button. `data-native` keeps a browser select. Menus in panels (Funktionen, Eigenschaft hinzufügen: `DropdownMenu` in `dropdownmenu.js`) open as such menus, too, with submenus.
- **View settings are toggles with a key, shown in the status bar** (`menu.js` hint `type: 'toggle'` with `get`; `refresh_toggles()`): Gitter (G), Verbindungen (V), Effekte bewegen (B) in the level editor (`LevelEditor.set_view_option`, which keeps the checkboxes under Werkzeuge in step) and Zwiebelhaut (O) in the sprite editor (`Canvas.set_onion_skin`/`update_onion_skin`: the frame before, reddish, and after, bluish, shine through under the drawing; animations loop; remembered per browser). A disabled status-bar entry dims its text and keys only, never the line between the entries.
- **A palette can convert the whole game** (`src/static/palette_apply.js`; Funktionen → Palette → Ganzes Spiel an Palette anpassen, or the checkbox in Palette wählen): every frame of every sprite (dithered, or `nearest`) and every colour a level stores (`palettize_level_colors`: background colour, Hintergrund colours and gradients, effect colours; alpha kept, never dithered). One step back is kept (`game.palette_undo`, Umfärben rückgängig machen). Not during a live session. The recipe build converts a scene with `szene.palette` the same way.
- **Pasted pictures are analysed before they come in** (`src/static/image_import.js`; Strg+V or dropping an image file in the sprite editor): a fake background around the border (one colour, or the two of a checkerboard) is removed by flood fill from the border; the pixel size (art pixels enlarged s times, also fractional, JPEG noise allowed) is the biggest grid whose lines catch the edges about as well as the best one (`grid_score`: better than chance) and that reproduces the picture (`reconstruction_error`); frames come from evenly spaced figures, a repeating column profile, or the sprite's size. The dialog shows the guess and lets the child change it (background, pixel size, columns × rows, where to insert: replace the frame, append, new state, new sprite). Nothing is scaled except by whole detected art pixels; when the frames do not match the sprite's size it warns and offers to enlarge the sprite (all frames bottom-centred, like Größe ändern), to place the frames bottom-centred (saying that what does not fit is cut off) or a new sprite; an empty single-frame sprite simply takes the picture's size. Several picture files at once (dropped, pasted or Funktionen → Sprite → Bilder öffnen …) are the frames of one animation, sorted by the last number in their names (`sort_by_frame_number`); each gets its own background removed, they share the pixel size most of them have, and all are cut to one common box so the animation keeps its alignment (`process_image_series`). The analysis works on plain RGBA arrays and has tests (`test/image_import.test.cjs`).
- **Level undo/redo compares versions instead of recording actions** (`src/static/level_history.js`). Per level id, the history keeps the level as JSON after the last completed edit; `LevelEditor.history_observe()` runs after every mouse/touch release, key release and (after a typing pause) field change in the level pane, and a difference becomes one step. New editing paths are covered automatically; they only need to finish within such an event. Showing a level must not create a step: the level and layer click handlers end with `history_rebase()` (the layer panel fills in missing settings), and so does entering the level pane. Undo puts the older version into `game.data.levels` and reloads the editor (`reload_level_keeping_view`); in a session it is sent like any other edit, and it is refused while somebody else holds the level. Anything else that replaces a level's data must call `game.level_history.forget(id)` first (collaboration does), so nobody undoes somebody else's work. A new game (`_load` with other data) starts a new history. Strg+Z/Strg+Y are matched by the printed letter (`e.key`), not the key position, because Z and Y swap on German keyboards; inside text fields the browser's own undo applies.
- **The level pane's side columns grow on wide screens** (`handleResize` in `studio.js`: from 1600 px the right column is 300 px and the left one 276 px, else 216/222 px; the level view takes the rest). The level and layer lists fill the right column (`#main_div_level .full_right_menu_container` in `styles.css`), so placed-sprite properties keep their labels at 1920 × 1080.
- **The game gets the keys in the Spielen pane:** after a test run starts (or the pane opens), the studio focuses the game frame (`focus_play_frame`, `window.focus()` in `start_playtest`), and keys that still arrive at the studio while the pane is shown are handed to the frame (except Strg/Alt shortcuts and F11).
- **Test runs never change the game:** "Level testen" (level editor, key T) calls `window.studio_start_playtest({ level_index, start })`; the Spielen pane saves a temporary copy as always and calls `game.start_playtest()` in the frame, which skips the start screen and curtain and may put the player character at `start` (lifted out of solid blocks; respawns there too). R restarts, Esc calls `end_playtest()` → `window.studio_return_from_playtest()`. The normal Spielen tab and `#mi_start` clear `game.playtest`, so ordinary play is unchanged.
- **Movement and gravity remain separate ideas:** Keep control, movement/physics, abilities and presentation conceptually separate. Variable gravity/camera changes must be opt-in; old games retain established downward gravity.

## Student-facing language and help

All student-facing labels, explanations, hints, tutorials, and warnings must be **in German**. Retain established gaming terms such as *Hitbox*, *Knockback*, *Cooldown*, and *Coyote Time*, explaining them in German as needed. Make doors and keys easier to configure with contextual help: explain `geschlossen`/`geöffnet` states, the optional `Übergang` animation, and matching door/key codes on placed sprites. Do not overwrite student artwork.

## Code map

- `src/static/traits.js`: trait and state metadata.
- `src/static/game.js`: studio editor and data normalization (`fix_game_data`).
- `src/static/palette_apply.js`: converting a whole game (sprites and level colours) to a palette.
- `src/static/image_import.js`: Bild einfügen – analysing a pasted or dropped picture (background, pixel size, frames) and the dialog.
- `src/static/sprite_actions.js`: the sprite editor's right-click menus (duplicate sprites and states, copy, cut, paste and move frames, swap animations).
- `src/static/sprite_basket.js`: Sprites aus einem anderen Spiel holen (basket dialog, `copy_sprites_for`, `Game.add_sprites`).
- `src/static/own_game.js`: Als eigenes Spiel weiterführen (the dialog and `Game.save_as_own_game`).
- `src/static/game_ids.js`: stable sprite/level IDs (`ensure_game_ids`, `assign_new_game_id`) and ID-based sprite references (`convert_sprite_references_to_ids`, `resolve_sprite_references_to_indices`, `remove_sprite_references`).
- `src/static/level_editor.js`, `src/static/widgets.js`: placement controls and UI widgets (a layer can be locked against accidental edits: `layer.properties.locked`, absent = unlocked and removed again on unlocking, editor-only; every editing path checks `layer_locked`/`refuse_locked_layer`, so new ones must too; the current layer's name is shown in a corner of the level view (`update_layer_label`), and a double-click with the select tool picks the sprite under the mouse in any visible layer and switches to that layer, again at the same spot the one behind it (`placed_sprites_at`/`next_pick` in `level_selection.js`, which also convert the point per layer for Parallaxe)); `src/static/level_history.js`: level undo/redo; `src/static/level_selection.js`: moving, copying, pasting, duplicating, filling, moving selected placed sprites between layers, selecting every copy of the selected sprites ("Alle gleichen") and replacing them with another sprite ("Ersetzen durch": same place and array order, placed settings kept only for traits the new sprite has, a new Schalter/Druckplatte gets a free Code) (pure functions on a layer's `sprites`; a layer holds one sprite per exact position, so whatever is moved, pasted or filled in replaces what was there, like painting). Letter shortcuts in the level editor (Strg+C/X/V/D/Z/Y) are matched by `e.key`, never by key position.
- `src/static/app.js`: gameplay runtime, door/key interactions, collisions, camera.
- `src/static/layer_fade.js`: fading a whole layer (its own material copies) for Signale.
- `src/static/speech.js`: Sprechtexte – fonts, settings, sentences, timing, wrapping and the pixel rasterizer (the render pass is `Game.draw_speech` in `app.js`).
- `src/static/signals.js`: Signale – the per-level bus, door and layer reactions, and the editor's "what else has this Code" line.
- `src/static/movement_regions.js`: opt-in Bewegungsbereiche (swim, float, other gravity, currents) for the player character and walking enemies, per rectangle layer or for the whole level.
- `src/static/combat.js`, `src/static/combat_swing.js`, `src/static/combat_projectile.js`, `src/static/combat_melee_trait.js`: shared attack, melee, projectile/bomb deliveries and legacy/new trait adapters.
- `rezepte/`: German how-to recipes for the Hilfe tab. `rezepte/tools/build.mjs` records each recipe's GIF from the real engine in headless Chromium, checks the recipe's promised outcome and writes `src/static/rezepte/` (commit the generated files). Rebuild after gameplay changes; a failing recipe means children would be told something that no longer works. See `rezepte/README.md`. The build also writes every recipe's scene as an openable game (`spiele/<id>.json`, `spiel` in `rezepte.json`); the Hilfe tab opens it in the studio (`rezepte.js`) with `game.from_recipe` set, and `Game.save` then asks for an own title and author instead of saving the recipe (own_game.js, mode `recipe`). `from_recipe` is session-only, cleared by every `_load`, and live sessions refuse to start from a recipe scene.
