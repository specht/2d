# 2D Game Studio — notes for future development sessions

Read `TODO.md` and inspect the current repository before proposing changes. This is a visual game-making tool used by children, and hundreds of existing games have been saved. The TODO is a collection of ideas and reports, **not** a list of verified bugs or approved feature designs.

## Working agreement

- **Advice and patches only.** Never push to GitHub, create remote branches or pull requests, commit changes, or modify this repository on the user's behalf. Provide a patch based on the current branch for the user to inspect and apply locally. Do not assume a previous patch or this file has been applied.
- **Saved JSON is a compatibility contract.** Old game descriptions must load unchanged. Preserve existing trait/state/property names, array layouts, defaults, references, and the meaning of absent fields. Do not require users to migrate or re-export games. New features should use optional fields with legacy-compatible defaults. When modernizing mechanics, prefer a runtime compatibility adapter over rewriting stored JSON; keep legacy semantics and define explicit precedence if old and new fields coexist. Compatibility is one-way: saving may write a newer format, because only the current code reads saved games. `fix_game_data` must stay deterministic (the same JSON always normalizes to the same result), since content-derived tags and recipe fingerprints depend on it.
- **Preserve established gameplay.** Runtime internals may change, but assess any visible change to old games. Identify an intentional bug fix and its compatibility implications instead of silently changing existing behavior. Do not enable formerly ignored level-completion conditions for old games without a compatibility strategy.
- **Small, focused patches.** Implement one agreed issue or milestone at a time, explain the change and give practical checks for existing and new games. Add focused automated tests where they help; never substitute isolated tests for browser/gameplay verification.
- Keep the visual trait-based editor approachable. Separate **control**, **movement/physics**, **abilities** and **presentation** where practical; combine capabilities through traits instead of hardcoding platformer-only character classes. Do not begin a wholesale ECS/physics rewrite.

## Established behavior and design boundaries

- **Seamless interiors are built with Signale:** a Bereich over the house sends its Code while the player's centre is inside, and the facade/roof layer reacts with "weg, solange an" (optionally fading). There is no separate visibility system any more: old Sichtbarkeitsbereiche (`visibility_region` layers) are promoted to Bereiche on load (see Signale). Facade/roof art should have collision disabled, because a layer that is away also does not collide.
- **Combat foundation is implemented:** Shared actor/baddie melee, ranged projectiles and timed bombs; preserve legacy attacks and J/K/F controls. New attack families must use the same owner-neutral combat machinery for actor and baddie from their first playable version rather than creating a second enemy-only or player-only damage system.
- **Combat rules are independent of artwork:** Delivery, targeting, damage, timing and hit geometry come from combat configuration and runtime state, never from image pixels, frame count or sprite colour. Optional attack/hit/death animation states are presentation and must not silently change damage or collision semantics. Projectiles and other attack visuals likewise do not inherit unrelated placed-sprite traits.
- **Future combat stays incremental:** Instant lasers/rays, reusable area attacks, cooldown feedback and finite ammunition remain separate backlog items. A continuous beam is a distinct mechanic from an instant ray because it needs explicit re-hit/interrupt timing.
- **Collaboration is explicit and capability-by-link:** Do not introduce accounts, ownership or private-game permissions just to support live collaboration. A normal public game code may continue to let anybody open and save a descendant, but joining an active shared editing session requires its own hard-to-guess temporary session link/code. Every participant supplies a session-local display name; use it for presence and lock/conflict messages, but never treat it as authentication or durable ownership metadata. Address sprites and levels by their durable `id`, never by array index; keep session-only metadata (participants, locks, revisions) out of saved JSON. Prefer server-authoritative revisions and small resource leases/locks for the first implementation over a wholesale CRDT rewrite. The server never interprets references between resources; every editor action that adds, deletes or moves a sprite or level must call `window.collaboration?.structure_changed(kind, action, id)` after changing the local list (and lists offer `can_delete_index` so a locked item cannot be deleted). Anything that replaces the studio's game with another one must not do so silently during a session: `game.load()` is already guarded, other paths call `window.collaboration.confirm_leave('load', proceed)` first. Switching between sprites or levels must not flash or dim the editor: a resource is editable at once unless somebody else holds its lock; the client keeps the last server-confirmed value of every resource (`server_values`), sends what differs once its lock arrives, and undoes it if somebody else was faster. Showing a sprite must not change its data (the canvas does not re-encode a frame it only displays). Participant colours are indices handed out by the server (`COLOR_COUNT` in `collaboration.rb`) and mapped to `COLLABORATION_COLORS` in `collaboration.js`; keep both lengths equal. Shared saves must still go through the established immutable game/version path. `raw/collaboration/sessions.json` holds session codes and reconnect tokens: never move it below `gen/` or anywhere else nginx serves.
- **Sprites and levels have stable IDs:** Every sprite and level carries a durable `id` (`src/static/game_ids.js`). `fix_game_data` fills in missing, invalid or duplicate IDs deterministically from the position (old games get `s0`, `s1`, … and `l0`, …) and never changes an existing valid ID. Editor actions that create a sprite or level must call `assign_new_game_id` before adding it, so a new object never inherits the ID of a deleted one. References to sprites are stored as sprite IDs: slot 0 of a placed sprite, `hit_sprite_id`/`attack_sprite_id`/`projectile_sprite_id` in attack visuals, `traits.baddie.drop.sprite_id` and `sprite_id` of `need_sprite` conditions. Old games hold indices in the legacy fields (`*_sprite_index`, `sprite_index`, slot 0); `fix_game_data` converts them, and an ID wins if both exist. The game engine keeps working with indices: `app.js` calls `resolve_sprite_references_to_indices` when it loads a game, which also drops references to sprites that no longer exist. The studio keeps unknown IDs until a sprite is deleted (`remove_sprite_references`), and the level editor drops placed sprites whose sprite is missing. Reordering sprites never rewrites references. Any new kind of sprite reference must be added to the walker in `game_ids.js`. State references inside one sprite (door states and the like) are still indices.
- **Signale connect senders and receivers by Code, within one level** (`src/static/signals.js`). Every Code is stored as `signal_code`: placed `key`/`door`/`switch`/`pressure_plate`/`baddie` properties, layer `properties`, `traits.baddie.drop`, and `level.properties.signal_all_defeated`. What a sprite *is* (key, Schalter, door, how a door opens) belongs to its drawing; what it is *connected to* belongs to each placed copy, so one drawing serves different connections. Hence the loot key of an enemy takes the placed `baddie.drop_code` (absent = the drawing's `traits.baddie.drop.signal_code`, the only Code older games have; `effective_loot_code`), and such an enemy counts as a sender in the editor (`placed_signal_roles`, role `loot`). A placed door may override its drawing's `lockable`/`automatic` (placed `door.lockable`/`door.automatic`, true or false; absent = as drawn; `door_setting`). Older games stored keys and doors (and loot) as `door_code` and had Sichtbarkeitsbereiche; `promote_legacy_signals` turns both into the new form, deterministically, in `fix_game_data` and when `app.js` loads a game (so old saved games play the same without being re-saved; a `signal_code` that is already there wins). Senders: a key when collected (an; it still sets `found_keys`), a Schalter (`switch`, only when the action key goes down), a Druckplatte (while the player's centre is above it), a Bereich (`signal_area` layer: an while the player's centre is in one of its rectangles, aus when it leaves; evaluated at once at level start and respawn, so a figure starting inside sees the right picture without a fade), a defeated enemy (placed `baddie.signal_on_defeat`, absent = sends nothing) and the level when no enemy is left (`signal_all_defeated`; enemies on a layer that is away do not count yet, so waves work). Receivers decide what a signal means: a door by its placed `door_reaction` (absent = `unlock`, exactly the old key behaviour; the other reactions move the door themselves, also a locked one, and a door that is still moving does the last signal afterwards), and any sprite or backdrop layer by `properties.signal_code`/`signal_reaction`/`signal_fade` (absent = it does not react). A layer that is away is neither drawn nor collides, and its enemies wait (`signal_hidden`: no simulation, no contact damage, `CombatSystem.owner_is_alive` false). Its drawing fades over `signal_fade` seconds (default `SIGNAL_LAYER_FADE_SECONDS`) with its own material copies (`layer_fade.js`; enemies on it get theirs via `material_for_frame`); collisions switch at the moment of the signal. Every collision query goes through `Game.collision_candidates`; combat obstacle checks skip hidden entries too. Only the layer with the player never reacts. Every level starts with a new `SignalBus` in `setup()`; receivers keep their state when the player dies; a Schalter that starts *an* sends *aus* when first flipped; objects created later miss earlier signals; `SIGNAL_MAX_DEPTH` stops loops. Senders may send later (Verzögerung): placed `signal_delay` of a key, Schalter, Druckplatte or enemy, `properties.signal_delay` of a Bereich, `level.properties.signal_all_defeated_delay` (absent/0 = at once, at most `SIGNAL_DELAY_MAX_SECONDS`). Senders call `SignalBus.send`, which queues a delayed signal; `simulation_step` delivers what is due (`deliver_due`). Every signal arrives that much later, *an* and *aus* alike and in the order sent (an echo, not a timer that restarts); the sender's own picture (a Schalter's or Druckplatte's state) changes at once. Deciding at once (`signals.immediate`: level start, respawn, test start) ignores the Verzögerung and takes back what that sender still has on its way (`from`). A placed door may close again by itself (`door.close_after`, absent/0 = stays open; `door_auto_close_step`): the time counts from when it is fully open and starts again whenever it is asked to open while open (so an automatic door stays open while the figure stands in front of it); it closes doors whose drawing is not `closable`, too, and waits while the figure or an enemy overlaps the door. A door closed by a signal or the action key still does not wait. New editor objects that send get a free Code (`free_signal_code`), so they never start something by accident: Bereiche, *alle Gegner besiegt*, newly placed Schalter and Druckplatten (`give_new_senders_codes`, pen and fill) and an enemy whose *sendet, wenn besiegt* is switched on without a Code (`give_defeat_sender_code`). Keys and doors still start on 0, where they have always met; a Code that is already there (also 0 typed in) is never replaced. The level editor draws connections from senders to receivers as animated dashes with marching frames (`LevelEditor.build_signal_links`, from `signal_objects`/`signal_links`): for the selection or the current layer, or all of them with "Verbindungen zeigen". The "Verbinden" tool (R) connects two things by clicking them (`pick_signal_object` looks for a sender first, then a receiver; `connect_signal_objects` keeps a Code that already links one of them to something else, never reuses 0, and gives the receiver a sensible reaction if it had none); it refuses to make a layer react to a sender that lies on that same layer. New senders and receivers connect to the same bus and use `signal_code` instead of adding a second linking system; recipes check them end to end (`erwartet: signale`).
- **Level undo/redo compares versions instead of recording actions** (`src/static/level_history.js`). Per level id, the history keeps the level as JSON after the last completed edit; `LevelEditor.history_observe()` runs after every mouse/touch release, key release and (after a typing pause) field change in the level pane, and a difference becomes one step. New editing paths are covered automatically; they only need to finish within such an event. Showing a level must not create a step: the level and layer click handlers end with `history_rebase()` (the layer panel fills in missing settings), and so does entering the level pane. Undo puts the older version into `game.data.levels` and reloads the editor (`reload_level_keeping_view`); in a session it is sent like any other edit, and it is refused while somebody else holds the level. Anything else that replaces a level's data must call `game.level_history.forget(id)` first (collaboration does), so nobody undoes somebody else's work. A new game (`_load` with other data) starts a new history. Strg+Z/Strg+Y are matched by the printed letter (`e.key`), not the key position, because Z and Y swap on German keyboards; inside text fields the browser's own undo applies.
- **Test runs never change the game:** "Level testen" (level editor, key T) calls `window.studio_start_playtest({ level_index, start })`; the Spielen pane saves a temporary copy as always and calls `game.start_playtest()` in the frame, which skips the start screen and curtain and may put the player character at `start` (lifted out of solid blocks; respawns there too). R restarts, Esc calls `end_playtest()` → `window.studio_return_from_playtest()`. The normal Spielen tab and `#mi_start` clear `game.playtest`, so ordinary play is unchanged.
- **Movement and gravity remain separate ideas:** Keep control, movement/physics, abilities and presentation conceptually separate. Variable gravity/camera changes must be opt-in; old games retain established downward gravity.

## Student-facing language and help

All student-facing labels, explanations, hints, tutorials, and warnings must be **in German**. Retain established gaming terms such as *Hitbox*, *Knockback*, *Cooldown*, and *Coyote Time*, explaining them in German as needed. Make doors and keys easier to configure with contextual help: explain `geschlossen`/`geöffnet` states, the optional `Übergang` animation, and matching door/key codes on placed sprites. Do not overwrite student artwork.

## Code map

- `src/static/traits.js`: trait and state metadata.
- `src/static/game.js`: studio editor and data normalization (`fix_game_data`).
- `src/static/game_ids.js`: stable sprite/level IDs (`ensure_game_ids`, `assign_new_game_id`) and ID-based sprite references (`convert_sprite_references_to_ids`, `resolve_sprite_references_to_indices`, `remove_sprite_references`).
- `src/static/level_editor.js`, `src/static/widgets.js`: placement controls and UI widgets; `src/static/level_history.js`: level undo/redo; `src/static/level_selection.js`: moving, copying, pasting, duplicating, filling and moving selected placed sprites between layers (pure functions on a layer's `sprites`; a layer holds one sprite per exact position, so whatever is moved, pasted or filled in replaces what was there, like painting). Letter shortcuts in the level editor (Strg+C/X/V/D/Z/Y) are matched by `e.key`, never by key position.
- `src/static/app.js`: gameplay runtime, door/key interactions, collisions, camera.
- `src/static/layer_fade.js`: fading a whole layer (its own material copies) for Signale.
- `src/static/signals.js`: Signale – the per-level bus, door and layer reactions, and the editor's "what else has this Code" line.
- `src/static/movement_regions.js`: opt-in Bewegungsbereiche (swim, float, other gravity, currents) for the player character and walking enemies, per rectangle layer or for the whole level.
- `src/static/combat.js`, `src/static/combat_swing.js`, `src/static/combat_projectile.js`, `src/static/combat_melee_trait.js`: shared attack, melee, projectile/bomb deliveries and legacy/new trait adapters.
- `rezepte/`: German how-to recipes for the Hilfe tab. `rezepte/tools/build.mjs` records each recipe's GIF from the real engine in headless Chromium, checks the recipe's promised outcome and writes `src/static/rezepte/` (commit the generated files). Rebuild after gameplay changes; a failing recipe means children would be told something that no longer works. See `rezepte/README.md`.
- `TODO.md`: active backlog and open design questions. It is not proof that a reported bug still exists; verify current source and behaviour before implementing an item.

Be clear whether an observation came from source review, an isolated check, or a real browser/gameplay test. Never claim existing games were tested unless they actually were.
